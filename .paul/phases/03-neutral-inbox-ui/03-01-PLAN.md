<objective>
## Goal

Give the neutral `channelThreads` projection a real screen: pick a channel, see
its threads, open one, read the normalized messages, and reply with text —
so the Leo Hub round trip can be exercised from the product instead of from
Settings or a test file.

## Purpose

Phase 2 built the read surface and deliberately left it headless, gated behind
the first real round trip. The operator now wants to connect a WhatsApp number
through the Hub and test the whole thing end to end. Without a screen, inbound
messages are only visible in the Settings activity panel and there is no way to
reply in context.

## Output

A `/app/channel-inbox` route, neutral in naming and independent of the legacy
`/app/inbox`, so removing the laboratory later means deleting this directory
without touching the WhatsApp inbox.
</objective>

<acceptance_criteria>

## AC-1: Threads are listed per channel
```gherkin
Given a tenant with a lab channel that has two threads
When an authenticated member opens /app/channel-inbox
Then both threads are listed newest-first with preview, unread count,
     and an indication of whether the 24h service window is open
And a tenant with no neutral channels sees an empty state pointing at Settings
```

## AC-2: A thread opens and shows its normalized messages
```gherkin
Given a thread with inbound messages and status events
When the member opens that thread
Then inbound message text is rendered in reading order, oldest at the top
And status-only events do not render as chat bubbles
```

## AC-3: Replying is possible, and blocked states are explained
```gherkin
Given a thread whose channel has sendMode "disabled"
When the member opens it
Then the composer is disabled and states that the kill switch is active
Given the channel is in "allowlist" mode and the recipient is not allowlisted
When the member sends
Then the failure is shown as a readable message, not a raw error code
```

## AC-4: Opening a thread clears its unread count
```gherkin
Given a thread with unreadCount 2
When the member opens that thread
Then unreadCount becomes 0
And no other thread's unread count changes
```

## AC-5: Tenant fences hold on the new mutation
```gherkin
Given Tenant A owns a thread
When a member of Tenant B calls the mark-read mutation with that thread id
Then it throws and Tenant A's thread is unchanged
```

## AC-6: The legacy inbox is untouched
```gherkin
Given the new route exists
When the full suite and build run
Then /app/inbox and its components are unchanged
And no neutral component imports from components/inbox
```
