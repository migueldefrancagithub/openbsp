<objective>
## Goal

Stop inbound Hub activity from being stranded in `channelEvents`. Make delivery
statuses settle the `channelOutbox` row they belong to under a strictly
monotonic ladder, and project inbound events into a channel-neutral thread
table that a multichannel inbox can read.

## Purpose

Two entries in the `docs/HANDOFF-LEO-HUB-LAB.md` "Known limitations" list are
the only things keeping the laboratory from being observable as a real inbox:

- "Delivery/read status events are stored neutrally but do not yet reconcile the
  corresponding `channelOutbox` row."
- "Hub inbound events are visible in the laboratory activity panel but are not
  mirrored into the legacy WhatsApp `conversations/messages` tables."

The second one must **not** be solved by mirroring into legacy tables.
`conversations.phoneNumberId` is `v.id("phoneNumbers")`, so mirroring a
laboratory channel would require minting fake WhatsApp phone-number rows —
ADR-002 forbids the laboratory from reaching into the WhatsApp domain. A neutral
thread projection is the boundary-respecting route, and it is the same surface
Instagram will need in Phase 4.

## Output

- Neutral `channelThreads` table plus two new indexes.
- A pure, provider-agnostic outbox status ladder module.
- Reconciliation and projection applied inside the existing ingest transaction.
- Tenant-scoped inbox queries.
- Two new test files.
- Handoff limitations list updated to reflect what is now closed.
</objective>

<acceptance_criteria>

## AC-1: Status events settle the matching outbox row
```gherkin
Given an outbox row in status "accepted" with providerMessageId "wamid.TEST1"
When a normalized "status.delivered" event carrying id "wamid.TEST1" is ingested
Then that outbox row's status becomes "delivered"
And its updatedAt advances
And no other outbox row is modified
```

## AC-2: The ladder is strictly monotonic and never regresses
```gherkin
Given an outbox row already in status "read"
When a late "status.sent" or "status.delivered" event for the same
     providerMessageId is ingested
Then the row remains "read"
And the event is still persisted as evidence in channelEvents
```

## AC-3: Definitive success is never downgraded by a later failure
```gherkin
Given an outbox row in status "delivered"
When a "status.failed" event for the same providerMessageId is ingested
Then the row remains "delivered"
And failureReason records the provider's stated reason for operator review
And status is not changed to "failed"
```

## AC-4: Replay creates one event and applies the ladder once
```gherkin
Given a "status.delivered" event that has already been ingested
When the identical provider payload is delivered again
Then channelEvents contains exactly one row for that eventKey
And the outbox row is unchanged by the replay
```

## AC-5: Inbound messages project into exactly one neutral thread
```gherkin
Given a channel with no threads
When two inbound "message.text" events arrive with the same threadKey
Then exactly one channelThreads row exists for (channelId, threadKey)
And lastInboundAt equals the newer event's timestamp
And unreadCount is 2
And serviceWindowExpiresAt equals the newer inbound timestamp plus 24 hours
```

## AC-6: Tenant fences hold on every new read path
```gherkin
Given Tenant A owns a channel with threads and events
When an authenticated member of Tenant B calls the new inbox queries
     with Tenant A's channelId or threadKey
Then the call throws CHANNEL_NOT_FOUND
And no Tenant A row is returned
```

## AC-7: The legacy WhatsApp path is untouched
```gherkin
Given the laboratory ingest path runs reconciliation and projection
When the full test suite runs
Then no conversations, messages, or phoneNumbers row is created by that path
And convex/_test/providerIndependence.test.ts remains green
```

       `.index("by_channel_thread", ["channelId", "threadKey", "receivedAt"])`.
    4. Add a `channelThreads` table:

       - `threadKey: v.string()`
       - `identityId: v.optional(v.id("channelIdentities"))`
       - `lastEventAt: v.number()`, `lastEventKind: v.string()`
       - `lastInboundAt: v.optional(v.number())`
       - `lastOutboundAt: v.optional(v.number())`
       - `lastPreview: v.optional(v.string())` — truncated, see below
       - `unreadCount: v.number()`
       - `serviceWindowExpiresAt: v.optional(v.number())`
       - `createdAt: v.number()`, `updatedAt: v.number()`
       - `.index("by_channel_thread", ["channelId", "threadKey"])`
       - `.index("by_channel_last_event", ["channelId", "lastEventAt"])`
       - `.index("by_tenant_last_event", ["tenantId", "lastEventAt"])`

    Create `app/convex/lib/channels/outboxStatus.ts` as a **pure module with no
    Convex imports**, so it unit-tests without a database harness and stays
    reusable by the Instagram adapter in Phase 4:

    - Export `OUTBOX_STATUS_RANK`, a record giving each status a rank:
      queued 0, dispatching 1, accepted 2, delivered 3, read 4.
      `failed` and `unknown` are deliberately **off-ladder** — they are
      outcomes, not progress, so they get no rank.
    - Export `mapProviderStatusToOutboxStatus(eventKind)` translating
      "status.sent" to "accepted", "status.delivered" to "delivered",
      "status.read" to "read", "status.failed" to "failed". Return null for
      anything unrecognized so unknown provider vocabulary is ignored rather
      than guessed at.
    - Export `decideOutboxTransition({ current, incoming })` returning
      `{ nextStatus: string | null, recordFailureReason: boolean }`:
      - If `incoming` is null, return `{ nextStatus: null, recordFailureReason: false }`.
      - If `current` is a terminal success ("delivered" or "read") and
        `incoming` is "failed", return `{ nextStatus: null, recordFailureReason: true }`.
        This is AC-3: keep the proven outcome, keep the evidence.
      - If `incoming` is "failed" and `current` is not a terminal success,
        return `{ nextStatus: "failed", recordFailureReason: true }`.
      - Never return "unknown" as a nextStatus. `unknown` is only ever written
        by the dispatch path, never by inbound evidence.
      - Otherwise compare ranks and only advance:
        return `nextStatus` when `rank(incoming) > rank(current)`, else null.

    Write `app/convex/_test/channelOutboxStatus.test.ts` covering the ladder
    directly: forward advance, out-of-order regression blocked, read above
    delivered, failed-after-delivered preserved, unrecognized kind ignored,
    and `unknown` never produced as an output.

    Avoid: writing the reconciliation database logic here. Task 1 is schema
    plus pure decision logic only, so the ladder can be proven before it is
    wired into a transaction.

  <name>Task 2: Reconcile statuses and project threads inside the ingest transaction</name>
  <files>app/convex/lib/channels/projection.ts, app/convex/leoHubLab.ts</files>
  <action>
    Create `app/convex/lib/channels/projection.ts` exporting two async helpers
    that take the mutation `ctx` as their first argument. They are plain
    functions, not Convex mutations, because Convex mutations cannot call other
    mutations and both must run in the **same transaction** as the event insert
    — that is what makes reconciliation crash-safe without a scheduler.

    1. `reconcileOutboxFromStatus(ctx, { channel, event })`:
       - Read the provider message ID from `event.providerEventId`.
         If absent, return without side effects.
       - Look up the outbox row via the new
         `by_channel_provider_message` index scoped to `channel._id`.
         If no row matches, return — a status for a message OpenBSP did not
         send is evidence only, not an error.
       - Call `mapProviderStatusToOutboxStatus` then `decideOutboxTransition`.
       - Patch only when `nextStatus` is non-null, and always bump `updatedAt`
         when anything is written.
       - When `recordFailureReason` is true, write a truncated
         `failureReason` (cap at 500 chars, matching `_settleOutbox`).
       - When advancing off `unknown` is not possible because the row has no
         providerMessageId, do nothing — see the scope limit below.
       - Never clear `providerMessageId`, never decrement `dispatchAttempts`,
         never re-enter `dispatching`.

    2. `projectThreadFromEvent(ctx, { channel, event, identityId, now })`:
       - Return early when `event.threadKey` is absent.
       - Upsert `channelThreads` on the `by_channel_thread` index.
       - `lastEventAt` = `event.providerTimestamp ?? now`, but only advance it;
         a late-arriving older event must not rewind the thread ordering.
       - For `direction === "incoming"`: set `lastInboundAt`, increment
         `unreadCount`, and set `serviceWindowExpiresAt` to
         `lastInboundAt + 24 * 60 * 60 * 1000`.
       - For `direction === "outgoing"`: set `lastOutboundAt` and leave
         `unreadCount` untouched.
       - `lastPreview`: derive from the normalized payload — prefer
         `payload.normalizedText`, then `payload.message.text.body`. Truncate to
         160 characters. Never fall back to serializing the whole payload: raw
         provider payloads are evidence and must not leak into a preview field
         that the browser reads.
       - Carry `identityId` when the caller resolved one.

    In `app/convex/leoHubLab.ts`, inside `ingestWebhookEvents`:
       - Keep the existing dedup guard exactly as it is. Reconciliation and
         projection run **only for newly inserted events**, never on the
         duplicate branch — that is what makes AC-4 hold.
       - Capture the identity `_id` from the existing upsert branch so it can be
         passed to the projection instead of re-querying.
       - After each successful `channelEvents` insert: call
         `reconcileOutboxFromStatus` when `eventKind` starts with "status.",
         and call `projectThreadFromEvent` for every event that has a
         `threadKey`.
       - Do not change the returned `{ accepted, duplicates }` shape; the
         webhook route and existing tests depend on it.

    Avoid: importing anything from `convex/messages.ts`,
    `convex/whatsappAccounts.ts`, or `convex/lib/meta/*`. Avoid writing to
    `conversations`, `messages`, `contacts`, or `phoneNumbers` —
    `providerIndependence.test.ts` and ADR-002 both forbid it.

## SCOPE LIMITS

- **Backend only.** No changes to `LeoHubLabSection.tsx` or any UI. Wiring the
  inbox into a screen is a later plan, once the real round trip has passed.
- **No mirroring into legacy tables.** Explicitly out of scope by ADR-002, for
  the `phoneNumberId` reason stated in the objective.
- **No chatbot or flow-runtime changes.** That is Phase 3.
- **`unknown` outbox rows stay unresolved.** A row that went `unknown` because
  the send timed out has no `providerMessageId`, so no inbound status can match
  it. Resolving those needs a provider-side message lookup, which is separate
  work — record it as a remaining limitation, do not guess a match by recipient
  and timestamp. Guessing here would risk marking an unsent message delivered.
- **No new dependencies.**
- **No `.env` or deployment changes**, no `convex deploy`, no production
  credentials. `npx convex codegen` only.
- **No normalization changes** in `integrations/leoHub/webhook.ts` — the
  existing `status:` and `message:` eventKey shapes are the input contract this
  plan consumes.
